# Managed authentication feasibility for the Swiss-hosted MVP

Verified: 2026-09-08  
Issue: [#29](https://github.com/lbise/easy-quote/issues/29)  
Binding policy: [#16](https://github.com/lbise/easy-quote/issues/16#issuecomment-5580585487)

## Scope and conclusion

This is a bounded comparison of Clerk and ZITADEL Cloud. It does not select either product, create an account, or approve processing outside Switzerland. The application, database, PDFs, and backups remain Swiss-hosted. The identity provider receives only the minimum identity data needed for authentication, such as immutable subject ID, verified email, password and MFA material, and necessary device, IP, and security-event data. It must never receive Customer records, Customer Notes, Quote content, PDFs, or Business Guidance.

Both products can plausibly provide managed verified-email/password authentication and MFA recovery codes. Neither is approved for real use yet. Their public DPAs allow or describe processing beyond Switzerland and the EEA, including subprocessor paths. The product owner must separately approve exact country flows, support access, logs, and safeguards before any real identity data is sent.

There are two candidate configurations worth carrying forward to a disposable acceptance test:

1. **Clerk Pro plus the Swiss application host.** It has a direct, signed-claim reverification mechanism for application actions and documented backup-code UX. Its hard design gap is staff-only MFA. Clerk documents `Require multi-factor authentication` as an instance-wide switch, not a role policy. A possible application configuration leaves provider MFA optional for Artisans, but the Fastify server authorizes staff functions only when a validated Clerk assertion proves an enrolled and recently verified second factor. This is an application authorization check, not a replacement MFA system. It needs an acceptance test and an explicit decision that a staff user may complete primary sign-in but may access no staff function until MFA is enrolled. Clerk's hosted Account Portal remains English, so French requires app-hosted Clerk components. The outstanding Q13 preference for provider-hosted login has not been accepted.
2. **ZITADEL Cloud Free for a pilot under 100 DAU, plus the Swiss host.** It publishes Swiss residency as a Cloud option, organization-level login policies, hosted username/password login, password reset, and a recovery-code API. It has a clean path to Artisans with optional MFA and staff in an organization whose login policy requires a factor, provided the policy and account-routing behavior are tested. Its hosted Login V2 can use `fr-CH` translations, but the public docs do not prove that a complete French pack is supplied. The team would need to configure and test the translation. The free plan's 100 daily-active-user limit and unspecified support scope make it a pilot candidate only.

ZITADEL Pro starts at USD 100/month before the Swiss application host. It does not establish the CHF 100 total target. Clerk Pro is cheaper on its published list price but still needs country approval and a total-cost calculation. These are candidates, not a recommendation to purchase or provision.

## Cost boundary

The CHF 100 is a total pilot-infrastructure target, not an identity-only budget. The Swiss-hosting research gives an indicative floor of **CHF 22.18/month excluding VAT**. It is not a final hosting budget.

The following uses only public provider list prices. It assumes one production application, fewer than the included user limit, no SMS, no paid support add-on, no overages, no custom domain unless stated, no external SMTP charge, and no cost for monitoring, PDF generation, backups beyond the Swiss host, or implementation. The pricing pages quote USD, so a CHF total needs the exchange rate available when a purchase is actually considered.

## Correction to the earlier Auth0 inference

The earlier #26 note correctly found that Auth0's documented Enterprise session-management endpoint and price did not establish a compliant all-device provider-session solution on a lower plan. That does **not** prove that a lower plan makes all-device *application access* impossible.

An application ordinarily owns server-side sessions, authorization grants, download permissions, and background-job permissions. It can immediately deny every local session and authorization grant for an identity, while the managed provider handles password verification, email verification, MFA, recovery codes, and its own refresh/session credentials. It must still test the provider's actual refresh and access-token behaviour. This is not permission to reimplement passwords, MFA, recovery codes, or an identity service.

The same distinction applies to Clerk and ZITADEL above. Provider session termination alone is insufficient evidence for the Fastify API and PDFs. Conversely, the absence of a generic provider "terminate every session" endpoint does not alone disqualify a provider if the combined provider and ordinary application controls demonstrably stop all continued access.

## Evidence gaps and pilot acceptance tests

No missing public documentation is proof of impossibility. It is an approval gap. Before sending even real identity data, use only disposable non-customer test users and obtain written answers or run tests for:

1. exact tenant, log, backup, notification, support, staff-access and subprocessor countries, plus DPA and transfer safeguards for the selected plan;
2. verified email/password and reset, including delivery provider and SMTP configuration;
3. MFA enrollment, recovery-code display, storage warning, one-time redemption, regeneration and the policy that staff never receive an assisted bypass;
4. Artisan optional MFA and staff mandatory MFA, including a direct attempt to enter staff functions without a second factor;
5. browser and phone sessions, 30-day idle expiry, maximum lifetime, refresh-token expiry, and behavior after cookie loss;
6. export, Business deletion and security changes: a server-side fresh-auth check using a signed provider assertion, never browser time or JWT issuance time;
7. all-device sign-out: provider sessions, refresh, already-issued access tokens, Fastify sessions, every API route, PDFs and queued/background work; and
8. hosted EN/FR sign-in, reset, MFA and recovery screens. This is especially decisive for Clerk Account Portal and ZITADEL Login V2 fallback behavior.
